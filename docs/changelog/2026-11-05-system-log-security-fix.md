# 系统日志敏感信息修复

**更新日期：** 2026-11-05

**更新范围：** 安全审计 A11、系统日志写入、回归测试与隔离 Docker 验收。

## 问题与修复

原数据库日志会无差别保存完整请求参数和 URI；后台 POST 在处理前写日志，因此即使请求校验失败，密码、邮件或节点密钥及查询串凭据仍可能进入 `v2_log`。异常消息、上下文和文件日志也可能携带敏感值。

系统日志改为允许字段策略：数据库和配置的文件等应用日志通道使用相同安全处理器；只有固定允许的事件标题可原样记录，其余自由文本替换为 `[Log details omitted]`。不保存请求体、URL 查询串、任意上下文及异常消息或堆栈。后台 POST 使用固定标题，允许保留经过格式校验的后台控制器方法及正整数主体、目标 ID；数据库日志另保留时间、级别、经验证的请求方法和客户端 IP。异常对象仅保留类型、文件名和行号。数据库写入失败时文件回退也使用固定标题。Laravel emergency 文件通道使用相同处理器。

该策略刻意舍弃部分排障细节；新增事件标题须确保为固定且不含输入的文本并补充测试。配置以外的自建日志通道、第三方直接写入文件、反向代理及 PHP 等外部日志，以及邮件日志和失败队列等独立数据源不在此策略覆盖范围。更多说明见 [日志与敏感信息](../logging.md)。

Stripe、支付通知、流量与统计、自动续费、验证码等已有调用改为固定业务事件，并在可用时保留异常类型和位置；原 Stripe 完整订单日志不再写入。

## 部署与历史数据

修复不修改或追溯清理已存在的日志，不包含数据库迁移。部署时按[更新文档](../update.md)更新代码并重启 PHP-FPM、Horizon 和已启用的 Workerman；按实际留存政策处理历史 `v2_log`、文件、集中日志及备份，并根据实际暴露范围轮换凭据。不得把本地测试视为历史日志处置、密钥轮换或生产部署已经完成。
