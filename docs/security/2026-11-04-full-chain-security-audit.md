## 4. 问题详情与验收标准

### A01 / P1 — 授权缓存信任边界与撤销失效

**原审计基线代码位置：** `app/Services/AuthService.php:75-105,124-145`；`app/Http/Middleware/Admin.php:19-23`；`app/Http/Middleware/User.php:19-23`；`app/Http/Controllers/V1/Admin/UserController.php:146-186`。

`decryptAuthData()` 只在缓存未命中时验 JWT、查会话和读取角色，随后把角色缓存 3600 秒。缓存命中直接返回。`removeSession()` 删除会话目录，却不删除该 JWT 的缓存；再调用 `removeAllSession()` 时，这个已被删除的会话也不在可枚举目录中，缓存成为孤儿。后台撤销 `is_admin/is_staff` 没有同步失效授权缓存，原管理员在窗口内仍可使用后台更新接口把自己的 `is_admin` 改回 1。

另一个同根因分支：缓存键直接等于传入的 authorization，命中任意非空缓存项便跳过 JWT 验证。公开验证码可产生这样的字符串缓存项，实测它可以通过 User 中间件的真值检查。**这不等于能冒充某个用户或通过管理员检查**：后续读取 `user['id']` 的接口通常会类型报错；已经确认的是认证边界未执行其宣称的 JWT 校验。

**影响：** 被撤销的已缓存会话最多继续存活约一小时；被降权管理员可恢复后台权限，继而批量读取/导出用户和配置。不是普通用户无前提提权。

**修复方向：** 始终验证 JWT 及其结构；专用缓存前缀并校验返回结构；每次确认会话仍有效。采用用户 `auth_version`/权限版本或可原子撤销的会话记录，角色变化、禁用和撤销必须即时生效。不要让授权缓存成为独立的权威来源。

**验收：** 单会话删除后立即拒绝；先删单会话再全量注销仍拒绝；降权后旧 JWT 无法继续访问后台和恢复管理员；随机缓存键不能当作登录凭据。即时生效指撤销/角色变更成功后开始认证的新请求，不追溯取消已通过认证的在途请求。

**整改记录（2026-11-04）：** 已在 `app/Services/AuthService.php:78` 移除 JWT 对应的用户/角色缓存读取与写入。每次验 HS256 签名，校验正整数或等价正数字字符串 ID、非空字符串 session，查询有效会话，再用 `useWritePdo()` 读取最新用户角色及禁用状态。旧缓存、JWT 角色声明和普通缓存项都不能替代认证。既有合法 JWT 与会话格式保留，无数据库迁移。

新增/删除单个/清空会话统一使用用户级缓存锁，避免并发整图写回恢复已撤销会话；操作成功后清理可枚举的旧 JWT 缓存，认证安全不依赖旧缓存能否枚举。获取锁超时返回失败，登录未保存会话时返回 503。锁租期为 10 秒，保障以正常缓存 I/O 在租期内完成为前提；Redis 多进程与生产部署验收仍需单独执行。

正式回归 `tests/Unit/AuthSessionSecurityTest.php`：**30 项测试、180 个断言通过**；同样用例在独立进程预载旧基线 AuthService 时出现 **25 项失败、0 错误**，可检测原缺陷。两个离线脚本中的 A01 项已改为拒绝行为断言。A02 后台改密/快捷码问题保持待修复，不能由 A01 关闭推导为已解决。

### A02 / P1 — 密码重置未统一撤销既有认证能力

**代码位置：** `app/Http/Controllers/V1/Admin/UserController.php:146-186`；`app/Http/Controllers/V1/Passport/AuthController.php:210-255,267-311`；`app/Http/Controllers/V1/User/UserController.php:467-476`。

后台更新用户密码只保存新哈希，没有清除现有会话，只有 banned=1 分支触发注销。实测旧 JWT 在一小时授权缓存过期后仍可重新通过会话检查，因此该问题不会靠等缓存过期自行消失。

快捷登录 `TEMP_TOKEN` 仅保存 user ID，生命周期 60 秒，没有绑定密码/认证版本。即使找回密码成功并调用全量注销，重置前签发、仍未过期的快捷码仍可建立新会话。这个子问题有明确的剩余 60 秒窗口，不是长期可重放码。

**修复方向：** 用户改密、后台重置、找回、禁用、角色变更使用统一的凭据失效流程；快捷码绑定认证版本，原子消费，并在重置时失效。

**验收：** 后台改密后所有旧会话立即失效，超过缓存 TTL 仍不能恢复；重置前的快捷码失效，新签发码只可消费一次。已用真实控制器、验证器与内存 SQLite 验证上述两个缺陷。

### A03 / P1 — 用户接口泄露节点 TLS 私钥

**代码位置：** `app/Http/Controllers/V1/Admin/Server/V2nodeController.php:86-145`；`app/Services/ServerService.php:193-248`；`app/Http/Controllers/V1/User/ServerController.php:17-31`。

remote 证书模式生成并保存 `tls_settings.tls_key`。用户节点服务仅删除 `private_key`、`ech_key` 等字段，遗漏 `tls_key`；用户 `server/fetch` 把节点对象直接返回。所属节点组的普通有效用户可以取得实际 PEM 私钥。

**影响：** 节点身份私钥泄露；具备路由/流量劫持等额外条件时可冒充节点。不能由此推断能解密具有前向保密的历史 TLS 流量。

**修复方向：** 用户输出使用显式允许字段的 DTO；所有出口排除服务端私钥。核实过去是否已下发后，轮换受影响证书和私钥并同步 pin。

**验收：** 测试节点使用哨兵私钥，检查用户列表、订阅、App 配置等所有出口均不出现哨兵；客户端所需公钥/pin 保留。仅修一处前端显示不算完成。

### A04 / P1 — 一个节点凭据具有全体节点访问能力

**代码位置：** `app/Http/Routes/V1/ServerRoute.php:10-16`；`app/Http/Controllers/V1/Server/UniProxyController.php:21-51,214-310`；`app/Http/Controllers/V2/Server/ServerController.php:18-74`；`app/Services/ServerService.php:251-266,415-424`；其他三个 V1 节点控制器构造器。

节点只用统一 `server_token` 认证，`node_id/node_type` 由请求决定，没有把凭据绑定到固定节点。持有任一节点配置的人可以选择别的节点读取配置、其权限组的有效用户 ID/UUID，也可以访问上报接口。V2 节点配置包含服务端工作所需的完整 TLS/加密配置。

**影响：** 单节点主机失陷或不可信合作节点可横向扩散到其他线路及用户代理凭据。返回的是节点协议需要的用户集合，不是邮箱/密码等整张用户表。

**修复方向：** 每节点独立高熵凭据，服务器端解析并固定节点身份；统一约束用户、配置、流量和在线接口；支持单节点撤销、轮换，逐步淘汰全局兼容 key。

**验收：** A 节点凭据访问 B 节点的全部读写接口都必须拒绝，不能靠隐藏节点 ID；撤销 A 不影响 B。

### A05 / P1 — 节点流量上报缺少输入、范围及幂等校验

**代码位置：** `app/Http/Controllers/V1/Server/UniProxyController.php:72-91`；其他 V1 节点提交方法；`app/Services/UserService.php:225-230`；`app/Jobs/TrafficFetchJob.php:19,40-44`；`app/Console/Commands/TrafficUpdate.php:43-75`；`database/install.sql:609-611`。

上报 JSON 的 UID 和增量直接进入队列，随后对输入 UID 进行 Redis 整数累加，再按数据库中存在的用户写回。未校验用户是否属于该节点，缺少非负整数、大小上限和批次去重；数据库用量字段为有符号数。负数可抵消用量，任意现有用户 UID 可被额外扣量，重复上报/部分完成后的队列重试会重复累计；不存在的 UID 会被最终用户查询过滤。

**修复方向：** 把已认证节点范围与业务宽限规则落实到 UID 检查；限制结构、非负整数、单批大小和合理增量；以节点序号/批次 ID 原子去重，队列重试也幂等。即使完成 A04 仍需单独修复本项。

**验收：** 别组 UID、负数、超大值、错误结构和重复批次不产生计费写入；合法批次只累计一次。MySQL/Redis 并发与故障重试尚未在本轮执行。

### A06 / P1 — 有签名的非到账事件可被视作支付成功

**代码位置：** `app/Payments/Coinbase.php:61-83`；`app/Payments/BTCPay.php:63-99`；`app/Http/Controllers/V1/Guest/PaymentController.php:13-46`。

Coinbase 验签后直接取 metadata 和 event ID，不检查事件类型及付款状态。BTCPay 验签后查询 invoice，只取 metadata/orderId，不检查事件类型或发票结算状态。两者随后都进入通用 `paid()`。

**必要前提：** 对应网关已启用，且 webhook 配置会发送创建、待处理、过期等非最终成功事件。不能把“收到有效签名”当成“已经到账”。

**修复方向：** 按网关协议仅接受最终成功事件，核对商户/店铺、invoice、订单、应收金额和币种；非成功事件只记状态，不开通。BTCPay 官方将多种 invoice 生命周期事件分开定义，应按实际使用版本确认：[Greenfield API](https://docs.btcpayserver.org/API/Greenfield/v1/)。本项根据代码缺少任何状态分支确认；未做真实网关端到端付款验证。

**验收：** 使用已正确签名的 created/expired/failed 测试事件，断言订单未支付且无权益/余额发放；pending 的具体语义按网关版本与业务确认策略单独判定，不能一概等同于未收款；只有业务认可的最终成功事件触发一次发放。

### A07 / P1 — 回调没有完整绑定本地付款意图

**代码位置：** `app/Http/Controllers/V1/Guest/PaymentController.php:17-46`；`app/Services/PaymentService.php:17-38`；`app/Payments/CoinPayments.php:32-95`；`app/Http/Controllers/V1/User/OrderController.php:233-264`。

通用回调只接收 `trade_no/callback_no`，按订单号查单并入账，不比较订单的 `payment_id`、应收金额、币种或商户身份，也没有统一的外部交易唯一约束。各适配器即使验签，也无法在此层保证“该回调属于此订单的此付款尝试”。

CoinPayments 尤其需要优先复核：金额、币种和 `item_number` 通过浏览器跳转 URL 传出，通知阶段只验商户/HMAC/status，没有比较本地应收。如果网关接受被浏览器更改后的收银台参数，低额交易的真实通知也不能被此代码拦住。**代码缺少核对已确认；现行 CoinPayments 网关是否接受这条低额流程，仍需沙箱核验。**不能把有待验证的网关行为写成已实测资金损失。

**修复方向：** 创建不可变 payment attempt，保存通道/商户/币种/最小货币单位应收金额/外部 invoice；适配器返回结构化结果，由统一层严格比较后再支付。将手续费、换汇和实际入账单位纳入同一规则。外部交易 ID 与通道建立唯一约束。

**验收：** 有效签名但错误金额、币种、商户、通道、invoice 或订单均拒绝；同一个外部交易不能给两个订单发放权益。不能只测试签名篡改和同一顺序回调重放。

### A08 / P1 — paid/cancel 并发状态转换不互斥

**代码位置：** `app/Http/Controllers/V1/User/OrderController.php:175-224,303-324`；`app/Services/OrderService.php:259-269,484-506`；`app/Jobs/OrderHandleJob.php:38-56`。

余额在保存订单时预扣；取消流程条件更新 `status=0→2` 后退回余额，但 `paid()` 只检查内存中的旧 status，然后普通 `save()` 覆盖为 1。若支付路径先读到 0、取消提交退款、支付路径再保存，已取消订单可恢复为待开通；零应付的余额订单也进入此分支。`open()` 的 1→3 检查无法阻止先前 2→1 的非法转换。

**影响：** 并发交错下可能退款与套餐开通同时成立；重复回调也可能造成多次入队/通知。这里的风险来自应用状态机，不是通用“有事务就安全”。

**修复方向：** 用数据库条件更新或行锁保证支付、取消相互排斥；仅成功改变状态者产生后续副作用；用事务性 outbox/可靠补偿保证状态已支付但入队失败时可恢复。

**验收：** 隔离 MySQL 中固定交错测试：支付/取消任一胜出后另一个失败；退款与开通不能同时成功；并发相同回调只发放一次。当前为静态并发推理，未声称做过真实多连接压力复现。

### A09 / P1 — 礼品卡限次并发竞争

**代码位置：** `app/Http/Controllers/V1/User/UserController.php:157-261`；`app/Models/Giftcard.php:14-18`。

兑换开启事务，但礼品卡与用户查询没有 `lockForUpdate`；多个账户可同时读到同一个正的 `limit_use` 和旧 `used_user_ids`，各自发放权益，再以旧值保存剩余次数，丢失扣减和已用用户记录。单次卡首次读取空记录时也有该竞争窗口。

`used_user_ids` 已声明 array cast，却又 `json_decode()`/`json_encode()`，还存在类型混用：历史数据的具体编码决定后续是否出现 PHP 8 TypeError。这是应一起修复的功能缺陷，不能拿可能直接报错的顺序兑换流程证明可以无限重复兑换。

**修复方向：** 锁定礼品卡和相关用户行；建立独立兑换流水及 `(card_id,user_id)` 唯一约束；限次条件扣减与权益发放在同一事务；使用 cast 后的数组类型。

**验收：** 两个账户并发兑换单次卡最多一笔成功；同一账户并发只发放一次；有限次、无限次和历史 used_user_ids 编码均验证。需在隔离 MySQL 复核，SQLite 单连接不能证明并发安全。

### A10 / P1 — 空回调密钥没有失败关闭

**代码位置：** `app/Http/Controllers/V1/Admin/PaymentController.php:73-85`；`app/Payments/Coinbase.php:70`；`app/Payments/BTCPay.php:75`；`app/Payments/CoinPayments.php:77`；`app/Payments/StripeALL.php:147-154`；其他 Stripe 适配器的 `notify()`。

后台只要求 config 存在，不对各适配器必需 secret 做字段验证；上述适配器把可能为空的 secret 直接交给 HMAC/Stripe 验签。空字符串 HMAC 是可计算的值，不会自动等同于禁用通道。不同于 EPay/BEasy 等已有的非空校验，这些路径尚未统一防护。

**必要前提：** 对应通道已启用、回调 secret 实际为空，且回调地址/订单标识可取得。本轮没有读取真实配置，不能断言生产存在空密钥。BTCPay 还会查询其配置的发票接口，不能忽略该额外依赖。

**修复方向：** 适配器声明必需配置 schema；保存、启用和每次回调均校验非空有效 secret；错误配置拒绝启用/处理并给管理员明确提示。不要以可猜测的回调路径代替签名强度。

**验收：** 每个适配器的 missing/null/empty/空白 secret 都应拒绝，合法 key 与错误签名的行为分别验证；禁止只覆盖某三个历史已修适配器。

### A11 / P2 — 默认日志把凭据复制进数据库

**代码位置：** `config/logging.php:20`；`app/Logging/MysqlLoggerHandler.php:20-39`；`app/Http/Middleware/RequestLog.php:16-22`；`app/Http/Routes/V1/AdminRoute.php:11-13`。

默认日志通道为 mysql。handler 无差别保存 `request()->all()` 和完整 `getRequestUri()`；后台 POST 的 log 中间件使配置/改密请求在进入处理前即落日志，校验失败也不例外。因此 email_password、server_token、payment config 内的 secret、用户新密码、通过 query/body 传入的 auth_data 等会有额外副本。不能据此声称所有正常登录请求必然有明文密码日志，只有触发日志的请求成立。

**影响：** 原本只能访问日志/备份的人得到更多凭据；管理会话泄露或日志暴露后影响扩大。应用自身的 `getSystemLog` 仍受管理员中间件保护，没有确认它匿名公开。

**修复方向：** 日志只保留允许字段和操作主体/目标 ID，递归脱敏嵌套 config、异常 context 和 URL query；不要序列化整个请求。依照留存政策处理历史敏感日志，并按实际暴露范围轮换凭据。

**验收：** 密码、邮件/节点/支付 key、JWT、验证码的哨兵值都不得出现在数据库/文件/异常日志，保留有用操作信息。已用真实 RequestLog + MysqlLoggerHandler 写入内存库，确认四类哨兵被保存。

### A12 / P2 — SVG 验证码缺少人机验证作用

### A13 / P2 — Webman 请求中 exit 结束工作进程

**代码位置：** `app/Http/Controllers/V2/Server/ServerController.php:20-48`；`app/Http/Routes/V2/ServerRoute.php:13-16`；`webman.php:21-37`；`start.php:56-70`。

**验收：** 同一个 worker 处理缺 token、错 token、无节点后仍能处理下一条正常请求；连接正常关闭，PID 不因这些请求改变。

### A14 / 策略观察 — 假地址仅覆盖订阅，不覆盖网站节点列表

### A16 / P2 — 支付请求关闭服务端证书验证

**代码位置：** `app/Payments/BEasyPaymentUSDT.php:52`；`app/Payments/Epusdt.php:71,100`。

### A17 / P2 — 生成账号的可预测初始密码

### A18 / P2 — 叠加减免产生负价并放大换套餐退款

**代码位置：** `app/Services/CouponService.php:25-38`；`app/Services/OrderService.php:113-137,55-56`；`app/Http/Controllers/V1/User/OrderController.php:164-175`。

优惠券自身的折扣金额被限制到原价，但随后 `setVipDiscount()` 又加上原价乘用户折扣，未限制总减免，导致 `total_amount` 为负数。接下来的换套餐分支以 `surplus_amount-total_amount` 计算退款并把应付归零，负价格可变成超出旧套餐剩余价值的额外退款。

例如原价 100 元、券减免 90%、用户折扣减免 20%，计算应付为 -10 元；若换套餐剩余价值为 0，退款计算变为 10 元。它不依赖单项配置大于 100%，但需要两种正常配置同时满足上述组合。没有实测生产资金流。

**修复方向：** 明确减免叠加策略，将总减免限制在原价范围，进入折抵前强制非负应付；退款以可核验的历史实付剩余价值为上限，金额统一使用整数最小货币单位。

**验收：** 合计减免小于/等于/大于 100%、有/无旧套餐剩余价值、零价/充值订单分别验证；新订单促销不得凭空创造历史退款价值。

### A19 / P2 — 优惠券每用户限次缺少待支付预占

**代码位置：** `app/Http/Controllers/V1/User/OrderController.php:79-82,156-175`；`app/Services/CouponService.php:19,75-81`；`app/Services/UserService.php:218-222`。

## 6. 已检查、当前不列为已证实漏洞的事项

- **员工提权旧代码：** `StaffRoute.php:10-39` 路由整体注释。Staff 更新控制器能力过大，应在重新启用前收紧，但不能当成当前可访问的员工提权入口。
- **用户订单/工单 IDOR：** 已核对主要 fetch/detail/reply/close/cancel 查询中的 user_id 范围；未确认普通用户可直接读写他人订单/工单。管理员查询全用户本来就是其权限，不能独立当成 IDOR。
- **SQL 注入：** 核对 filter/排序、邮箱查找、审计检索和 raw SQL。多数为参数绑定；节点路由 FIELD 参数先 intval；流量最终 UID 来自数据库，流量值经 Redis 整数运算。没有把“出现 raw SQL”直接定性为脱库入口。
- **文件/代码执行：** Theme 名称在写入入口受现有主题清单限制，配置内容使用 var_export；协议枚举固定本地目录。未发现直接由普通输入拼接的 eval/exec/unserialize 上传执行链。公共主题 HTML 是管理员可配置功能，未据此报告普通用户存储 XSS。
- **工单 XSS：** 自带后台工单消息/标题主要作为 React 文本子节点输出，未确认用户消息直接进入 HTML sink；知识库/公告允许管理员富文本并不等于普通用户能够写入。前端依赖和其它自定义主题仍需单独审查。
- **图床 SSRF/上传：** 出站 URL 已要求 HTTPS 公网 DNS、检查解析 IP、固定 CURLOPT_RESOLVE 并禁止跳转，图片有限额和 MIME 检查，文件转发外部图床而非本地 PHP 执行目录；没有重复报告此前已修的基础 SSRF。PHP 保留地址判断对 IPv6 过渡格式等边界及部署代理仍建议隔离回归，未确认完整可利用绕过链。

- **Horizon：** `config/horizon.php:92` 已加 admin 中间件，不能仅因为 APP_ENV=local 或默认 gate 逻辑就报告匿名公开。
- **Webman 可信代理：** 当前 `TrustProxies.php:28-45` 已限制到配置的代理，默认 loopback，不信任 forwarded Host/Port；相关回归通过。A13 是独立的进程生命周期问题。

## 7. 仍需部署/产品确认的事项

这些不计入上述 18 项修复清单事项；发现相应配置后可转成独立工单。A14 的产品策略观察也需要单独决策：

1. **会话和工单 IP 直接信任请求头。** `AuthService.php:22-53` 直接优先 CF-Connecting-IP/XFF；`User/TicketController.php:366-375` 直接用 X-Real-IP/XFF 并同步请求明文 HTTP 地理位置接口。即使框架可信代理已修，旁路读头仍可能污染审计/归属信息。应统一 `$request->ip()`、按可信链恢复地址，将地理查询移到有超时和脱敏的异步流程；没有确认它导致登录权限绕过或任意主机 SSRF。
2. **Telegram webhook 停用与空配置。** `Guest/TelegramController.php:17` 只比较 bot_token 的 MD5，未拒绝空 token 或检查 bot_enable；URL query secret 也有日志副本风险。需核实是否存在停用/清空 token 后遗留绑定账号。建议独立高熵 webhook secret header、关闭/空配置时拒绝、update_id 去重；不能在没读生产配置时认定匿名 Bot 管理权限已可利用。
3. **CORS。** 自定义 `CORS.php:16-33` 反射来源并允许 credentials，与 config/cors.php 不一致。但网站权限目前依赖显式 JWT，跨站页面不能自动读取 localStorage JWT；没有据此确认跨站整库读取。建议明确可信前端来源、Vary: Origin、预检与是否需要 credentials，并验证 passport session/captcha 行为。
4. **耗尽额度仍下发配置。** `UserService.php:147-152` 没检查 u+d，而节点 users 集合会检查。是否要求隐藏已耗尽账号的线路元数据应由产品确认；不能由此断言节点继续接受其代理流量。
5. **部署暴露和长驻状态。** 核实根目录是 public、.env/.git/SQL 备份不可访问、Redis/MySQL ACL、Webman 只允许代理接入、APP_DEBUG 关闭、服务 UID 与目录权限。仓库样例未证明这些服务对公网开放。Webman 的 Laravel 单例、URL/session/异常状态应做跨用户顺序请求隔离测试，目前未确认串号。
6. **外部服务与遗留适配器。** 现存 WechatPayNative 引用的 Omnipay 等依赖应核对部署是否实际可用；各网关现行事件语义、收银台参数约束、真实节点实现和自定义主题未做线上集成验证。下载执行可变分支脚本建议固定来源版本，但未发现供应链被植入证据。
7. **CSV 导出。** 用户导出通过字符串拼接，没有标准 CSV 引号/换行处理或公式前缀防护。建议标准编码并对外部可控单元格做公式安全处理；本轮未用实际 Excel/LibreOffice 证实特定注册邮箱可形成可执行公式，因此不报告“打开导出即 RCE”。
8. **佣金划转再返佣。** `User/UserController.php:426-445` 在佣金转余额订单仍为正 total_amount 时调用 setInvite，随后才归零并标完成；`CheckCommission.php:50-74,99-104` 未明确排除内部划转。存在上级及符合配置时可能为没有新收入的内部划转再发佣金。需确认产品是否允许该奖励；没有证实无本金无限提现。
9. **佣金发放并发。** `CheckCommission.php:63-75` 未锁订单或原子抢占，`Console/Kernel.php:36` 未配置任务防重叠，佣金流水缺少对应业务唯一约束；多 scheduler 或任务重叠时需验证重复发放。普通用户不能直接执行该命令。应增加幂等发放记录，并验证中途失败重试。
10. **余额/权益快照覆盖。** `OrderService.php:36-39` 在事务前载入用户，后续以旧 balance/套餐字段 save；与其他合法充值、消费、礼品卡或划转并发时可能覆盖已提交更新。应统一资金写入规则、锁用户或使用原子更新，在隔离 MySQL 做不同业务间的交错测试；不能由此宣称顺序重放同一回调会无限充值，末尾订单状态检查仍会回滚失败路径。
